Origin of the register (issue #78)#

This page preserves the content of issue #78, “Tracking: researched-but-deferred provider candidates”, so closing the issue loses nothing. It is a historical record: the verdicts below are the ones given when the issue was written. They were re-triaged by ADR 0005; the current state of every format is in the register.

Purpose of the issue#

The issue indexed candidate provider formats that had been researched. Each had its own issue with usage detail and a rationale, so the evaluation was not repeated and the reasoning for building or not building was discoverable.

Provenance#

Most candidates were surfaced by nur’s closest analog, task-keeper, a static multi-runner covering about 28 formats. They were cross-checked against nur’s supported and filed lists.

Re-analysis note (from #140)#

The original split assumed several formats “cannot be statically parsed”. That was imprecise. The ADR 0001 hard rule is that listing must not execute project code, and AST, text and comment parsing are safe. Task names are often statically discoverable even when the command body is imperative, and a delegated run command (invoke <name>, rake <name>, and so on) is legitimate. So invoke, nox and Rake were candidates, parked on value and reliability rather than safety, while GitHub Actions, Gradle/Maven, CMake and cargo-xtask were declined on honest, per-format grounds.

Declined with documented grounds#

The original reasons, per format. The current, gate-based records are in declined.

Format

Source file

Why declined

Issue

GitHub Actions

.github/workflows/*.yml

Parses fine, but not a local task runner (remote runners, ${{ }} / matrix / needs) and inherently multi-file versus the single-file scope. The highest adoption (~39,887) does not override this.

#147

Gradle / Maven

build.gradle(.kts) / pom.xml

Gradle’s task set is plugin- and runtime-produced (no reliable static parse). Maven’s runnable units are a fixed universal lifecycle, so pom.xml yields nothing project-specific. Gradle ~7,736.

#148

CMake

CMakeLists.txt

Imperative build generator, not a task runner; target names are variable-, loop- and generator-expression-driven; the two-step configure/build model leaves no clean delegated run. ~6,771.

#149

cargo-xtask

xtask/ crate

Not a format but a convention; subcommands are arbitrary Rust with no declarative file (.cargo/config.toml only proves the alias exists).

#150

The multi-file ground for GitHub Actions was retired when ADR 0004 replaced the single-file scope with a rooted scope.

Use case#

nur’s value depends on a hard guarantee: listing tasks never executes project code. As candidate formats are researched, some turn out to be safe to parse (even if only a subset), and some genuinely do not fit: not a local task runner (GitHub Actions), no reliable static parse (Gradle, CMake), or no declarative file at all (cargo-xtask). The issue indexed those decisions with their rationale so future contributors do not re-litigate them, and so the boundary of what nur will and will not support stays explicit. Candidates can be built when demand or value warrants; declines can be revisited if circumstances change.
